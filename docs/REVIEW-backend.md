# 后端独立可靠性审查

审查日期：2026-11-16。基线提交：`fd36b460602ae33ab3cb5aebd2f7aa337136558b`。运行环境：Windows，Node.js `v24.19.0`。

范围：`lib/inspect.js`、`lib/ops.js`、`lib/guard.js`、`lib/compose.js`；只为核实调用约束和错误传播读取了宿主路由、直接依赖和相关测试。唯一新增仓库文件为本报告，未改实现和测试。未读取真实 API key、真实会话或用户配置，未访问指定排除的目录或 3999 服务。既有单测自行使用系统临时目录中的合成夹具；补充故障注入全部使用进程内 Map 模拟文件系统，没有写真实指令文件。

结论：优先处理操作与撤销日志不同步、外部编辑被覆盖，以及检查请求缺少等待上限。下列发现具有代码或合成用例证据，但**未复现桌面版故障，不能把它们直接认定为“读取脉络中”的根因**。宿主 `/graph` 与 `/inspect` 是不同路由（`lib/host.js:84–88,104–105`），仍需主代理确认实际卡住的请求。

严重度：P1＝应优先修复的数据丢失或可用性问题；P2＝需要修复的可靠性/容量/边界处理问题；P3＝较低优先级缺陷。条件性风险和未验证事项另列，不宣称发现了所有问题。

## P1

### R01：业务改动成功后写日志失败，会产生“报失败但已生效且无法正常撤销”

- **位置**：`lib/ops.js:103–110,145–146,160–161,173–174,194–204`；错误传播：`lib/host.js:184–187`。
- **触发条件**：目标文件已替换或会话已归档/取消归档之后，`journal.json` 写入或 rename 因权限、空间、文件占用等失败；进程也可能在两个步骤之间退出。
- **证据**：内存文件系统在 journal 的 rename 阶段注入 `ENOSPC`。追加、移除、归档三个 Promise 都拒绝，但目标内容/归档状态已变化，而且没有日志条目。对一次正常追加执行撤销，再注入同一故障：原文已经恢复，journal 的 `undone` 仍不存在，再次撤销报“又被改过”。
- **影响**：客户端收到失败后可能重试追加，造成重复内容；界面没有记录可供撤销。撤销操作本身也会留下实际状态与记录不一致的结果。已有文件通常还留有备份，不能描述为所有原文均丢失，但备份与失败请求的关联不会正常返回。
- **建议**：先持久化带操作 ID、目标、前后哈希及备份路径的准备记录，再执行变更并提交状态；启动/重试时根据记录和哈希恢复。对已生效但日志提交失败返回明确的部分成功状态和恢复信息；使用操作 ID 防止重复追加。归档应记录意图并支持状态核对。
- **测试盲区**：现有 `tests/ops.test.mjs:16–32,75–93` 仅覆盖完整成功路径；没有“备份成功→业务提交成功→journal 失败”、撤销提交失败或重试幂等测试。

### R02：哈希只在读取时检查，提交前的外部编辑会被覆盖且不在备份中

- **位置**：`lib/ops.js:81–86,139–146,156–161,190–200`；最终替换：`lib/ops.js:44–49`。
- **触发条件**：编辑器、另一个进程或另一个 `createOps()` 实例，在读取旧内容之后、最终 rename/move 之前修改同一文件。实例内队列不能锁住这些写入者。
- **证据**：用内存文件系统在目标临时文件写入时插入一笔外部编辑。`append()` 成功返回，但最终文件和操作备份都没有外部新增内容。`removeBlock()` 的 expectedHash 和 `undo()` 的 afterHash 检查同样位于备份/异步写入之前，存在相同检查与使用间隔。
- **影响**：用户刚保存的编辑可能被旧快照覆盖；本操作备份无法找回这部分新增编辑。这与“撤销不覆盖后续改动”的保护意图不一致。
- **建议**：明确多写入者策略；对可协调实例使用共享路径锁，并在提交前重新检查文件身份/版本/哈希。仅增加一次哈希检查会缩短而不能彻底消除竞争窗口；若无法让外部编辑器参与锁，应采用可恢复的冲突副本/替换协议并明确保证范围。撤销新文件的 move 也需要同样处理。
- **测试盲区**：`tests/ops.test.mjs:101–108` 只覆盖一个实例内五次并发追加；`51–59` 只测试撤销开始前已发生的编辑，未测试操作执行中的编辑或多个实例。

### R03：检查历史会话没有超时或取消，依赖不返回时请求不会完成

- **位置**：`lib/inspect.js:88–91`；直接等待的调用链：`lib/host.js:84–88,184`。
- **触发条件**：`query.readSession(id)` 返回长期 pending 的 Promise，或者依赖内部 I/O 卡住且没有自身截止时间。
- **证据**：传入可手动释放的 pending `readSession`，观察 50 ms 后外层仍 pending，释放后才返回。代码中没有时间上限、AbortSignal 或断开连接取消逻辑；50 ms 是测试观测窗口，不是声称真实读取应在 50 ms 完成。
- **影响**：该模块无法保证检查请求最终返回错误或结果；在依赖不返回的条件下，客户端可以持续等待，刷新还可能累积重复工作。
- **建议**：为读取定义有限等待时间，超时返回可识别的 504/503；若 query 支持取消，传递取消信号并关联客户端断开。超时 Promise 包装本身不会终止底层 I/O，还需限制同一会话的并发读取。同步折叠的耗时需单独治理，见 R04。
- **测试盲区/限制**：`tests/inspect.test.mjs:77–81,100–106` 只覆盖立即返回的 mock；没有挂起、超时、取消或重复请求用例。未核实真实 DSH `readSession` 是否已有内部时限，未证明当前桌面加载停滞发生在此处。

## P2

### R04：事件数与单条展示截断没有约束总读取量、总响应体及同步计算量

- **位置**：`lib/inspect.js:12–19,26–34,39–40,57–59,63–65,80–84,91`；全字符 token 遍历：`lib/tokens.js:10–19`。
- **触发条件**：不足 50,001 条事件，但许多消息达到 20,000 字符，或少数消息原文非常大；大量 replace 还会反复扫描/移动 nodes。
- **证据**：1,000 条用户消息（每条 20,000 个 ASCII 字符）加 1 条回答正常通过；合成响应 JSON 为 **20,254,608 字节**，本机单次折叠约 **146 ms**，不含 JSON 序列化、读取及浏览器渲染。此时间是一次观测，不是稳定性能基准。允许的 50,000 事件若由 49,999 条这样的上下文和一条回答组成，仅 text 字段就接近十亿字符；这是上界推算，未实际进行大内存压测。
- **影响**：大响应和同步 token 估算/折叠会阻塞同一 Node 事件循环，并增加服务端、传输及客户端内存压力。`MAX_TEXT` 在拼接原文之后才截断，token 估算仍扫描完整原文；50,000 条检查发生在 `readSession()` 已读取日志之后，不能限制读取阶段。
- **建议**：为读取字节、累计可见字符、结果行数及响应字节设总量上限，返回明确的部分结果/分页信息；尽可能在 query 层做有限读取。对耗时折叠采用可让出事件循环的分批处理或 worker；避免对每个时间线预览先拼出完整回答。
- **测试盲区**：`tests/inspect.test.mjs:62–67` 只有单条 21,000 字符；缺少 50,000 边界、总量、超大单条、密集替换及并发响应测试。

### R05：不完整事件可以使整次检查失败，未来坏回答也会破坏较早回答的查看

- **位置**：`lib/inspect.js:13–17,27–28,32–34,39–42,80`。
- **触发条件**：content 中出现 null；content/changes/references 不是预期数组；tool/call 的 arguments 为对象；或用户选择的旧回答之后存在坏回答。
- **证据**：`content: [null]` 导致 `visibleText()` 访问 `b.type` 抛 TypeError；历史 seq=1 原本有效，但后续 seq=2 回答含 null block 时，`timeline = answers.map(...)` 仍扫描该回答并使 seq=1 的请求失败。工具调用 arguments 对象在 `entry()` 的 `.slice()` 处也抛 TypeError，而 `visibleText()` 对 tool-call block 的对象参数已经支持 JSON.stringify，处理不一致。
- **影响**：一条异常记录会挡住整个会话甚至不相关的旧回答，接口返回 500 而非可用的部分历史。
- **建议**：在输入边界验证事件、块、数组和参数形状；对坏条目标注 seq 和原因并降级展示；时间线摘要独立容错，不能让未来坏记录阻断选定历史。未知格式不能无提示地认作已进入上下文。
- **测试盲区/限制**：现有 fixture 都是人工构造的合规结构；没有 null、错类型或未来坏事件。尚未证明真实 DSH 会产出这些形状；若宿主保证强校验，应补充契约证据，否则应在插件边界防御。

### R06：拼盘清洗静默丢弃每项第 20,001 字符之后的内容

- **位置**：`lib/compose.js:23–24,39–47,135`；写入传播：`lib/host.js:140–147`。
- **触发条件**：任一 note/instruction/snippet 等 text 超过 20,000 字符。单个 20,001 字符 ASCII 项远低于 HTTP 512 KiB 上限，可以从接口进入。
- **证据**：20,001 个字符经 `sanitizeItems()` 后只保留 20,000；`compose()` 结果没有 clipped/truncated/originalLength 等标志。现有 `tests/compose.test.mjs:52–60` 明确断言截断，但没有要求告知用户。
- **影响**：关键约束、尾部结论或代码块结束标记可能消失；`/write` 可把不完整内容写入指令文件，而原始字符数和截断原因不再可见。
- **建议**：超限时拒绝并指出具体项，或显式返回原长度、保留长度和截断状态，要求用户能够检查实际写入内容；不要静默裁剪。同步调整“不会自动截断”的模块说明及测试契约。

### R07：损坏日志保全失败被吞掉，后续操作覆盖唯一旧日志

- **位置**：`lib/ops.js:90–99,107–110`。
- **触发条件**：journal 不能 JSON.parse，且移动/复制到 `.corrupt-*` 失败，但后续替换正常 journal 路径仍可成功。Windows 文件占用或不同目标权限可形成这种组合；真实文件系统组合未实测。
- **证据**：内存注入使 `.corrupt-*` 的 rename 和 copyFile 都失败；`readJournal()` 仍返回空数组。之后追加成功，journal 变成只有新操作的 JSON；没有保留下来的坏日志副本。
- **影响**：可供人工恢复的旧操作历史被覆盖，注释所承诺的“另存一份再从空开始”未成立。
- **建议**：保全失败必须中止后续 journal 写入，并返回原路径和失败原因；成功保全后才初始化。对可解析但结构不合法的 journal 也应显式报错/隔离，而非直接当空日志。
- **测试盲区**：`tests/ops.test.mjs:110–119` 只测试损坏文件成功迁移的情况。

### R08：可由 JSON 表达的非法日期通过清洗，使整个拼盘变成 500

- **位置**：`lib/compose.js:46,51–52,61`；HTTP 错误映射：`lib/host.js:185–187`。
- **触发条件**：snippet 的 `time` 为超出 Date 有效范围的数字，例如 `1e20`。
- **证据**：`compose(sanitizeItems([{kind:'snippet',text:'x',time:1e20}]))` 抛 `RangeError: Invalid time value`；直接调用已注册 HTTP handler 的合成 req/res 用例得到状态 500。
- **影响**：一个异常素材时间使全部素材的预览/写入失败；字段是客户端可控且合法 JSON，不应成为未分类服务端错误。
- **建议**：验证 Number.isFinite 和 Date 有效范围，非法时间省略日期并返回字段告警，或给出带字段位置的 400。
- **测试盲区**：只有正常日期，没有超范围、零值、负值或边界时间用例。

### R09：请求大小和业务输入校验没有对应的客户端错误状态

- **位置**：`lib/guard.js:46–55`，尤其 `52`；`lib/compose.js:32–38`；宿主映射 `lib/host.js:185–187`。
- **触发条件**：body 超过 512 KiB，或 items 不是数组/超过 200 项/类型非法。
- **证据**：readJson 超限抛普通 Error，没有 status；使用 Readable 合成请求调用已注册 `/compose` handler，512 KiB+1 请求和 `{items:'not-array'}` 都得到 500。现有 host 只把 SyntaxError 转为 400。
- **影响**：可预期的容量/用户输入错误被记录成服务端故障，客户端无法可靠区分需要缩小输入还是服务异常；自动重试也可能反复提交无效请求。
- **建议**：超体积使用 413、业务输入校验使用 400，并检查流终止后的 HTTP 响应交付策略；拒绝前可利用 Content-Length 预检，但仍保留流式计数以防 chunked/虚报长度。
- **测试盲区/限制**：`tests/host.test.mjs:35–39` 只断言 readJson 拒绝，不验 HTTP 状态。此次补充是 handler 级 req/res 测试；未验证真实 IncomingMessage 因 async iterator 退出被销毁时是否先断开 socket，需增加真实 HTTP 超限集成测试。

## P3

### R10：总 token 已超预算，但 overFrom 仍为 -1

- **位置**：`lib/compose.js:104,116–135`。
- **触发条件**：任务文字、起始标题、分隔符和拼接换行使总 tokens 超预算，但逐项 perItem 累积未超过预算。
- **证据**：一项 `{kind:'note',text:'x'}`，budget=10，task=`'z'.repeat(100)`，返回 `{tokens:37,budget:10,over:true,overFrom:-1,perItem:[1]}`。
- **影响**：超预算标志与定位位置不一致，界面无法指出超额来自任务或包装文本。这里只是展示预算，未发现它充当强制安全上限。
- **建议**：把任务/固定包装开销纳入同一累计口径，或增加明确的超额来源字段；计数应对应最终文本前缀而非单独取整后简单相加。
- **测试盲区**：现有预算用例由正文主导，没有“仅任务/包装超限”的情况。

### R11：临时文件写入失败不进入清理分支

- **位置**：`lib/ops.js:44–52`。
- **触发条件**：writeFile 创建临时文件并写入部分内容后失败，如 ENOSPC。该 await 在 try 之外。
- **证据**：内存注入先保留 partial 临时文件再抛 ENOSPC，atomicWrite 拒绝后 `.tmp` 仍存在。
- **影响**：重复失败积累临时文件及指令内容片段；rename 失败分支的 rm 若也失败，还可能遮蔽最初错误。
- **建议**：把 writeFile 和 rename 放入同一保护范围，以 finally 或保留原始异常的清理逻辑回收未提交临时文件；不删除已提交目标。
- **测试盲区**：没有部分写入失败、清理失败或遗留临时文件检查。

## 安全边界：已验证行为，但部署可利用性待核实

1. **Host 白名单不是客户端地址认证。** `lib/guard.js:12–15,24–42` 只检查请求头，不检查 peer address；合成请求的 `socket.remoteAddress='203.0.113.8'`，Host=`127.0.0.1:45678`，无 Origin，带正确 JSON/自定义头，仍返回 null（放行）。如果宿主监听非回环且无其他鉴权，远端普通 HTTP 客户端可自设这些头访问读写路由。这是已验证的模块行为，但**未检查真实监听地址、上游鉴权或代理，因此不把它宣称为已证实的远程漏洞**。应确认宿主强制回环绑定/鉴权；有代理时不能盲信客户端提供的转发头。
2. **“同源”只比较 host，不比较 scheme。** `lib/guard.js:30` 对 HTTP 请求和相同 host:port 的 HTTPS Origin 仍放行，合成用例已确认。若要求完整同源，应与可信服务 origin 比较协议、主机、规范化端口。浏览器端是否存在可利用路径、代理/TLS 行为均未验证。
3. **日志输出有白名单，但不是任意内容脱敏器。** `lib/inspect.js:83` 没有返回完整 request/header；既有测试只使用固定合成凭证占位符验证此点。可见正文、工具参数仍可能含用户放入其中的敏感文本；本次没有读取或搜索真实凭证，未据此声称泄漏。
4. **路径与文件身份保证有条件。** `lib/ops.js:70–71` 只校验 basename，公开 HTTP 路由另外通过项目/文件名约束生成路径（`lib/host.js:118–124,138–147`）。因此不能仅凭 ops 接受绝对路径就判定公开 API 存在任意路径写漏洞。符号链接、junction、硬链接、替换文件后的 ACL/mode 保留及可写 journal 的信任边界未实测，需单独核对。

## 修复复核追加：ops（2026-11-16）

本节覆盖本审查工程师后续获授权实施的修复；上面的初次审查证据保留，不能再把其中旧 ops 行号和旧行为当作当前实现。此次仅修改 `lib/ops.js`，新增 `tests/ops-recovery.test.mjs`，并追加本节；未改 README、其他实现或其他代理测试。

### R01、R07、R11 修复状态

- **R01 已处理，新增写前恢复记录。** journal 升级到 version 2，仍读取合法 version 1。文件备份和准备记录都使用独占临时文件写入、fsync、关闭和发布；`prepared`/`undo-prepared` 发布成功后才改文件或调用归档服务。准备日志失败时没有业务改动。业务已经生效但最后提交日志失败时，返回成功的操作及 `recoveryPending/recovery`，磁盘上准备记录保持可读；不把已完成的追加报为可重试失败。下次读取/写入前只核对哈希或归档状态，不重放业务动作；核对后的日志仍写不进去时拒绝新修改。不能核对的状态保留为 pending 或 conflict。
- **R07 已处理，保全失败停止操作。** 损坏日志先做独占副本、fsync、字节比对，并检查原日志没有在保全过程中变化；任何失败均保留原日志并拒绝业务修改。可解析但结构/版本不支持的日志即使保全成功也不会自动清空。只有无法解析且已成功保全的旧日志才重新初始化。
- **R11 已处理，清理覆盖部分写入和 fsync 失败。** 临时文件部分写入、fsync 或发布失败会尝试清理；清理失败保留最初异常，另附 `cleanupError/temporaryPath`。已成功发布的操作不会因临时文件清理失败被错误报告成业务未完成。进程直接退出无法执行 finally，遗留临时文件仍需后续人工清理，不宣称全部崩溃垃圾能自动回收。

### R02 缩小及保护范围

- 所有实例共享进程内队列；同 journal 和同文件还使用独占协作锁，防止本插件并发修改和操作记录互相覆盖。不同 dataDir 的实例修改同一文件也共享文件锁。
- 读取时核对普通文件及身份，临时内容写入、fsync 完成后，在最终发布前再次核对内容哈希和文件身份。同内容但换了 inode/身份的外部替换也会阻止提交。
- 新文件采用禁止覆盖的 link 发布；最后校验之后另一个编辑器新建的文件不会被覆盖。不支持该能力的文件系统会拒绝操作，不退回覆盖式写入。
- 撤销新建文件先在同目录 rename 捕获实际文件并复核；竞争期间变更的内容保存在暂存文件，能恢复时也采用不覆盖新目标的方式。跨卷只复制捕获文件并核验，不再“复制仍在使用的源文件然后删除源”；跨卷暂存文件保留，避免丢失仍持有句柄的编辑器写入。
- **仍有明确限制：已有文件的最后一次检查与 rename 之间不是 CAS。** 非协作编辑器仍可能在这个极小窗口写入，造成覆盖；当前跨平台 Node 文件 API 没有对这些外部写入者的统一比较并替换协议。本次仅缩小并测试其前后的常见窗口，不能宣称彻底解决 R02。路径别名/junction、不同版本不遵守锁的插件及其他写入者不在协作锁保证内。

### journal → 当前 UI 的兼容协议

`readJournal()` 输出保留 `id/label/undone/backup`，新增 `state/canUndo/recoveryPending/recovery`。用于显示的 label 前缀不写回原始操作名称；对于已保全的新文件撤销，显示用 backup 可以指向真实 retainedPath，磁盘记录中的原始 backup 含义不变。

| 返回状态 | undone | canUndo | 当前只检查 undone 的 UI | 后端行为 |
| --- | --- | --- | --- | --- |
| 旧版无 state / committed，且没有 recoveryPending | 空 | true | 显示撤销 | 再核对当前文件/服务并先写 undo-prepared，成功后撤销 |
| prepared | 空 | false | 仍可能显示按钮；label 为“待核对” | 先恢复；无法核对或锁占用时拒绝，不重放 |
| undo-prepared | 空 | false | 仍可能显示按钮；label 为“撤销待核对” | 先核对是否已撤销，不重复撤销 |
| cancelled | 空 | false | 仍可能显示按钮；label 为“未生效” | 拒绝自动撤销，业务未生效 |
| conflict | 空 | false | 仍可能显示按钮；label 为“待人工核对” | 拒绝该操作及同目标后续修改，保留恢复材料 |
| undone | 撤销时间 | false | 隐藏撤销、划线 | 已完成撤销，不再改文件 |
| 任意记录 recoveryPending=true | 不伪造时间 | false | 未撤销记录仍可能显示按钮；label 提示待恢复 | 必须先恢复记录/解除明确的锁问题 |

建议主代理将按钮条件设为 `!op.undone && op.canUndo !== false`，兼容旧数据；本工程师没有编辑 client。没有用假 undone 隐藏失败/冲突，否则会误报“已撤销”。即使 UI 尚未接入 canUndo，后端仍执行相同保护。

已完成普通历史保留 **200 条**；`prepared/undo-prepared/conflict` 全部额外保留，不因数量被淘汰，因此 journal 总条数允许超过 200。返回列表把需核对记录放在尾部，宿主现有 reverse 后优先显示这些记录。当前 UI 的前 30 条展示限制仍可能遮住超过 30 条的待核对记录，但数据不会因此删除。

### 恢复流程与剩余边界

1. 正常异常：刷新操作记录即可触发按哈希/归档状态核对；提交失败期间可以看到准备记录或内存核对结果及 recovery 提示。返回成功并带 recoveryPending 的操作不应按失败追加再试。
2. 崩溃遗留锁：`readJournal()` 会只读展示已有有效日志，不会抢锁或隐藏准备记录。先确认锁文件记录的旧进程已退出且没有操作运行，再人工移除明确对应的 `<dataDir>/ops.lock` 与目标旁 `.<文件名>.context-studio.lock`，随后刷新记录恢复。不要为清锁退出正在工作的用户进程。本次没有操作任何用户进程。
3. conflict 必须由操作者核对实际文件、备份、暂存与操作记录后人工处理；本次没有设计自动覆盖或自动删除冲突记录的入口。归档恢复需要服务公开 archivedSessionIds；缺少时保持 pending 并拒绝新的业务修改。
4. 文件内容执行了 fsync，但没有跨文件系统事务和统一的 Windows 目录持久化屏障，因此不承诺突然断电、内核崩溃或底层存储错误后的严格原子性。已测试的是正常 I/O 失败及真实子进程退出。
5. 协作锁不会解决无操作 ID 的客户端重复提交：一次明确成功后用户再次点击追加仍是一笔新操作。已经生效但网络响应丢失，且记录随后被正常完成的请求，无法与用户有意重复提交区分；没有宣称提供整个 HTTP 链路的 exactly-once。
