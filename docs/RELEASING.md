# 发版清单

每次发版（包括小版本）都按这个顺序逐项做，做完一项勾一项。

## 1. 代码和测试

- [ ] `npm test` 全部通过，记下用例数。
- [ ] 在隔离的 `DSH_HOME` 下实测新功能（不要用 3999 端口那个，也不要用日常 profile）。
- [ ] 用挂起读取、响应乱序、坏事件、存储失败及日志提交失败验证错误出口；检查未读取与不存在的区别。
- [ ] 原生桌面未实测时明确标注待验收，不能把隔离网页通过写成桌面通过。
- [ ] 回答排查切换早期 / 后期输出，确认后续消息不混入早期上下文；验证工具调用配对、局部选中文字、跨会话草稿来源和只预填不发送。
- [ ] 流转图验证前后输入差异、实际工具 ID 连线、线索定位与当前会话跟随；不能把推测边或合成错误当成历史事实。
- [ ] 会话整理确认前零生成；核对模型、范围、预算、完整发送内容；并发、取消、启动响应丢失、重启和存储失败不自动重放生成。
- [ ] 报告核对来源白名单、回答边界、截短/遗漏与实际用量；建议进入草稿保留 AI 标注，不覆盖任务或发送。演示适配器明确标为模拟并在隔离验收后卸载。
- [ ] 未经验证的真实模型质量、计费明确说明；没有用户对具体调用的确认，不以实测为由消耗真实 token。
- [ ] 供应商适配修复须核对安装版协议路径：例如 OpenCode 辅助调用携带稳定路由标识，错误保留安全分类与阶段；本机模拟通过不写成真实供应商通过。旧失败不能自动重放。
- [ ] 实测中发现并修复的问题，写进 `docs/DESIGN.md` 对应版本的「实测记录」。

## 2. 文档（README 要整篇过一遍，不能只加一节）

README 从头到尾每一节都要对照新功能检查：

- [ ] 顶部一句话介绍、首图：新功能是主角的话要换。
- [ ] 测试徽章的用例数。
- [ ] 「为什么要有拼图台」「核心理念」：新功能解决了新问题、带来新原则的，要补上。
- [ ] 「快速开始」：安装步骤；从旧版本升级的方法；打开后默认看到什么。
- [ ] 「界面一览」：整体布局说明；新功能单独一节并配截图；老的小节里因为新功能而改变的入口和操作。
- [ ] 「安全模型」：新的读写和新的操作要各占一行。
- [ ] 「配置」：新增的或含义变了的配置项。
- [ ] 「常见问题」：新功能最可能被问到的问题。
- [ ] 「工作原理」：新模块、新接口、新用到的 DSH 能力。
- [ ] 「路线图」：勾掉已完成的。
- [ ] 「参与开发」：测试用例数。

其他文档：

- [ ] `docs/DESIGN.md`：新版本的设计、DSH 源码出处、实测记录、已知限制；文首状态行。
- [ ] `CHANGELOG.md`：新版本条目。
- [ ] `package.json` 的 `version`。
- [ ] `docs/images/` 的截图，在 1440×900 下拍。
- [ ] 首图使用当前界面；保留旧功能截图时标明版本。不要用合成错误冒充真实会话实测。

## 3. 发布

- [ ] 提交，`git tag -a vX.Y.Z`，推送 `main` 和标签。
- [ ] GitHub Release：标题「vX.Y.Z · 一句话」，正文写新增、修复、安装 / 升级，并附截图。
- [ ] 打开仓库首页和 Release 页面，确认 README、图片、Latest 标记都正确。
