## R1：缓存数量上限没有约束定时器持有的日志

首轮代码在每次读取完成后创建捕获 `value` 的定时器；`value.promise` 的结果引用完整原始日志。`cache.delete()` 淘汰 Map 中的项，没有清除这个定时器。

反例在单独的 `node --expose-gc` 子进程运行：`maxEntries=2`、TTL 为 1 秒，连续读取 8 个不同会话；两次跨事件循环 GC 后，8 份日志全部存活；TTL 后再次 GC 才归零。该反例不依赖进程 RSS，也不证明现实会话已导致 OOM。其风险是短时间切换许多大历史时，实际保留数量由 TTL 内的吞吐量决定。

当前修复：`context-view.js:276` 的 `evict()` 清除定时器；刷新、服务切换及数量淘汰均使用它；已被淘汰的 pending 项完成后不再注册定时器。相同反例已通过。服务替换时旧请求完成不会覆盖新服务缓存的测试也通过。

## R2：来源信息应区分“不存在”与“无法读取”

首轮反例：`references` 为对象、`changes` 和 `sourceEventSeqs` 为字符串。正文仍可读，但这些来源被转为空数组，同时详情 `incomplete:false`，没有任何提示。

当前 `provenanceIssues()`（`context-view.js:26`）能识别非数组集合以及前 50 个元素中的非对象/非法事件序号，并校验实际输出的白名单字段；详情给出 notice，相关测试通过。超出检查/展示项数的关联有明确提示。

### R2b：数组元素是对象，但实际输出字段的类型错误

补充反例在修复前返回 `incomplete:false`：

```js
source: {
  kind: 'session-reference',
  references: [{ sessionId: {}, label: 42, truncated: 'true', omittedMessages: '7' }],
  changes: [{ path: {}, action: 42 }]
}
```

修复前，返回的引用变为 `{sessionId:'', label:'', truncated:false, omittedMessages:0}`，变更变为 `{path:'', action:''}`。目录同时可能因 `omittedMessages > 0` 的隐式转换给出“省略”线索，与详情里的零值矛盾。

原因是此前 `provenanceIssues()` 只检查 `record(x)`；`contextDetail()` 的来源映射直接 `cut()` / 转默认值，没有记录字段校验失败。

当前修复对实际读取的白名单字段检查字符串、布尔值及安全非负整数类型。上述反例现为 `incomplete:true`，包含引用和变更来源的异常提示，可读正文保留；字符串 `'7'` 不再触发实际省略消息的线索。独立测试还逐项覆盖会话编号、标签、截断布尔值、省略数量、捕获序号，包括负数、小数和超出安全整数范围的值；合法与缺失的可选字段不会误报。标准 DSH 已验证部分日志形状；此项是防御检查，不证明当前桌面会话含这种数据。

## R3：中断回答是诊断所需的历史事实

首轮用 `assistant/message.data.interrupted:true`，新 API 的回答、导航、详情均没有中断标记，也没有 warning。它会影响用户区分“推断错误”与“回答尚未完成”。

当前 `metadata()` 记录中断 issue；`navigation()` 返回 `interrupted`；`contextView()` 将选中回答的 issue 加入 warning（`context-view.js:63`、`:76`）。首轮回归通过。中断提示不应解释为模型推理过程的证明。

## R4：Unicode 分页与游标

首轮输入为 `a×11999 + 😀tail`，按 12,000 UTF-16 单元截取，使两页分别含高代理和低代理。拼回全文可以恢复，但单页显示和摘录无法保留完整字符。

当前 `sourcePage()` 在页首/页尾避开代理对边界，返回校正后的 `offset`；`contextDetail().row.textOffset` 使用实际偏移。以下测试通过：

- 普通边界以及位于代理对中间的请求偏移；返回文本和原文对应切片完全相等。
- 混合中文、扩展汉字、emoji、组合重音、ZWJ 序列与 CRLF 的 8 个文本块；所有顺序页拼回全文完全相等，页大小不超过上限。
- 顺序 `nextOffset` 所得页面的上一页终点等于当前页起点。

### R4b：任意偏移后的上一页可能重叠（P3）

`context-view.js:251` 用请求偏移计算 `previousStart`，向前跳过低代理后，上一页仍按固定最大长度取正文，不能总以校正后的当前偏移结尾。

可复现文本：

```js
const text = 'a'.repeat(11999) + '😀' + 'b'.repeat(11998)
  + '😎' + 'c'.repeat(24000)
```

| 请求 offset | 实际 offset | previousOffset | 前页 nextOffset | 结果 |
| --- | --- | --- | --- | --- |
| 24000 | 23999 | 12001 | 24001 | 重叠一个 emoji |
| 36000 | 36000 | 24001 | 36001 | 重叠一个字符 |

**此限制不影响已验证的从头顺序翻页。** 在测试中，从 `offset=0` 开始使用返回的 `nextOffset`，全文还原一致，没有遗漏或重复；这些顺序页对应的前页终点也已核对。

剩余问题限定于任意偏移/校正偏移后的反向导航。按本次明确的范围，UI 不暴露随机偏移跳转，暂不增加 `end` 参数，保留接口契约限制。UI 范围来自实现负责人的说明，本审查没有操作浏览器确认。若将来开放任意偏移跳转，需要重新定义前页的结束位置。组合字和 ZWJ 序列仍可能跨页，这是码点安全与字素安全的区别，当前测试没有要求按完整字素分页。

## R5：返回体有界，不等于同步计算量有界

位置：`argumentSource()`（`context-view.js:190`）、`sourcePage()`（`:208`）、每次读取重新调用 `indexContext()`（`:294`）。

修复前，每个正文页遍历最多 100,000 个内容块，并对每个对象形式的工具参数重新复制和序列化，包括完全不在当前页中的内容。单个参数的 2,000 节点、100,000 字符限制不能约束所有块的累计工作量。目录统计也逐条读取来源数组。

原始有界探针：1,500 个 `tool-call` 内容块，每个 `arguments:{body:'x'.repeat(95000)}`。修复前 `sourcePage(e)` 返回 12,000 字符，但计算的虚拟正文总长为 **142,538,998**，本机单次约 **381ms**。没有扩大到 100,000 块，也没有尝试耗尽内存；性能值会随机器与负载变化。

可复现核心代码：

```js
const content = Array.from({length:1500}, () => ({
  type:'tool-call', name:'x', arguments:{body:'x'.repeat(95000)}
}))
const e = {type:'assistant/message', data:{message:{content}}}
const start = performance.now()
const page = sourcePage(e)
console.log(page.text.length, page.totalChars, performance.now()-start)
```

当前每次 `sourcePage()` 的所有对象参数共享累计 **2,000 节点 / 100,000 字符**预算。超限用占位和 notice 明确表示，字符串正文和字符串形式参数不受这个对象预算截断。

原始反例现已加入测试：虚拟正文 **123,505 字符**，首次页本次约 **17ms**；`incomplete:true` 且含累计预算提示。`totalChars` 指带占位符的虚拟展示文本长度，不是原始对象参数的完整序列化长度。测试还验证 1,200 个小对象耗尽节点预算的情况，以及预算用尽后追加的长字符串正文、长字符串参数逐页拼回原文完全一致。

来源扫描也改为最多检查 50 项；一次补充复核发现详情 `sourceEventSeqs` 仍扫描 2,000 项，现已一并修复为先截取 50 项再过滤。观察数组访问索引的探针确认引用、变更、来源事件三类集合均未读取索引 50 及以后；过多关联有明确提示，正文保持可读。

此处关闭的是已复现的累计对象展开和来源扫描缺口。目录和正文仍有同步循环，每次请求仍重建索引；Host 定时器不能抢占正在执行的同步工作。这些保留为性能上限，不代表已做最坏负载证明，也不是桌面卡死根因的证明。

## R6：新增工具调用原文追溯的白名单

新增功能允许查看回答边界之前的 `tool/call` 原文，状态为 `source`；它不应计入已进入模型输入的消息数量。工具调用正文白名单为工具名和调用参数，未来调用和请求头仍不可读取。

补充反例将合成标记放入 `tool/call.data.message.content` 与 `data.message.source`。虽然 `sourcePage()` 正文没有展开这些字段，旧通用 `message()` 路径仍让标记进入 `row.preview`、来源名称、路径和引用字段。复核只使用 `SYNTHETIC_CALL_PRIVATE_SENTINEL`，没有读取真实秘密。

当前 `context-view.js:24` 仅对五种 `SURFACE` 消息类型读取通用消息；`tool/call` 不走该路径。新增独立测试检查 `body` 和 `arguments` 两种详情：可见调用参数保留、所有合成私有标记均未返回、未来调用和请求头拒绝、工具结果仍正确配对，调用记录不计作已进入模型输入。测试通过，白名单缺口已修复。

## 剩余限制与未覆盖范围

- 本报告不代表发现所有 bug。本分工没有浏览器操作或真实用户日志复现；上方真实 UI 记录来自主代理的隔离 4001 验收，不应混同为本分工的独立桌面验收。当前剩余限制以 [DESIGN 第 13 节](DESIGN.md) 的明确说明为准。
- R4b 是已接受的任意偏移反向游标限制；它不影响已验证的从头顺序翻页。将来开放随机跳转时需重新复核。
- 当前分页发生在 `readSession()` 返回完整快照之后。DSH 源码 `packages/session-query/session-query/src/types.ts` 将它定义为完整、脱离运行态的原始日志快照；首次底层读取与克隆的内存成本没有因 HTTP 分页消失。
- 两项缓存只限制条目数，尚无字节权重上限；R1 修复后的可释放性不等于可承受任意大日志。
- 缓存 10 秒后或服务更换时会取新快照。详情没有快照版本游标；如果宿主允许已存在事件发生投影/修复变化，需要另行验证跨页一致性。正常不可变前缀上的追加不是已证实的串页问题。
- 超过 250,000 前缀事件仍只保留导航/选中答案原文、模块计数标记不可用；回答导航先扫描全部事件，不是磁盘级流式分页。
- 保护边界下的可见字段不是通用脱敏器。用户正文或可见工具参数自身包含的秘密仍属于被展示内容；测试证明的是不展开不授权的额外字段。
- 来源关联数量、对象参数、附件和未知内容块有明确展示限制；分页不等于供应商最终请求还原，也不证明模型内部判断原因。
